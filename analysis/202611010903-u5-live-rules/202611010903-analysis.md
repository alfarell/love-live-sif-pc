# U5: live rules from the eboot (start)

Created: 202611010903 (Asia/Jakarta). Roadmap M4 item "Recover combo, score and hold rules from the eboot (U5)".

## 1. Tooling

- REA cannot analyze this file on Windows: its Ghidra provider accepts only PE files there; Hopper (macOS only), IDA and Kuna are not configured.
- Used instead: `llvm-objdump` from the installed Visual Studio LLVM toolset (`VC\Tools\Llvm\x64\bin`), no install. Full disassembly in `work/eboot.asm` (124 MB, not committed).
- Address mapping for `work/elf/eboot.elf`: virtual address = file offset − 0x4000 for the code/rodata segment. `work/eboot-strings.txt` lists file offsets.

## 2. `live_params.bin` loader and globals (function around 0x941F2–0x94400)

The loader looks up each `BLBN` symbol by name (`0x4bb4c0`) and copies it to a global:

| Symbol | Global | Accessor |
|---|---|---|
| `s_CommonParam` (500 bytes) | 0xE10CB0 | `0x946A0` returns its address |
| `s_EvaluateRangeDatas` | pointer 0xE10EA8, group count (size >> 5) 0xE10EB0 | `0x946B0` count, **`0x946C0(i)` = group i (32 bytes)** |
| `s_CalibrationData` (8 bytes) | 0xE10EF8 | `0x946D0` |
| `s_UserCalibrationData` (44 bytes) | 0xE10F00 | `0x946E0` |
| further symbols (`s_SkillAdjustDatas`, `s_LedControlParam`, cameras, …) | 0xE10F2C … | — |

`0x946C0` has only two callers: 0x9F609/0x9F62F (judge constructor) and 0xA01B3/0xA01CC (re-loading the windows; a skill widening the windows, *Hypothesis*).

## 3. Judge object (constructor 0x9F510, vtable 0xC03430)

| Offset | Content |
|---|---|
| +0x10 … +0x64 | 12 × (s32, bool) pairs, cleared (*Hypothesis:* per-lane input state) |
| +0x68, +0xA8 | window groups 0 and 1, base copies |
| +0x88, +0xC8 | window groups 0 and 1, active copies (`0x9F7A0` restores active from base) |
| +0xE8 | `s_CalibrationData` = {32, 16} |
| +0xF0 | `s_UserCalibrationData` = −80 … +80 (11 values) |
| +0x11C | the user's timing setting index (from a settings object at `[0xE04E20] + 0xE4FD8`) |
| +0x120 | frame/update counter (incremented each update) |

Inside group 0 at +0x88: early row +0x88 Bad, +0x8C Good, +0x90 Great, +0x94 Perfect; late row +0x98 Perfect, +0x9C Great, +0xA0 Good, +0xA4 Bad.

## 4. First rule recovered: built-in input offset

In the per-frame note update (0x9F7C0), the timing offset used for a note is:

`offset = s_UserCalibrationData[setting + 5] + s_CalibrationData[k]`

where `k` depends on an input-device type read per note/input (0x9F8E2–0x9F907, 0x9F9AA–0x9F9CB): type 1 uses `s_CalibrationData[0]` = **32 ms**; types 0 and 2 use `[1]` = **16 ms**. `setting + 5` indexes the 11-entry list (setting −5 … +5 → −80 … +80 ms).

So the game shifts judgement by a fixed 16 or 32 ms depending on the input device, on top of the user's adjustment. Which device type is which (controller, arcade buttons, …) is not resolved yet.

## 5. Note state machine (0x9F7C0, partial)

Note object: +0x3C lane (index into a per-lane table), +0x42 flags (0x10, 0x02 tested), +0x44 state, +0x54 start time, +0x58 hold length, +0x70 a counter. States seen: 1 (waiting), 2 (*Hypothesis:* being held), 3 (*Hypothesis:* hold release phase), 4 (finished; set by `0x9E8A0(note, 4)`). Current time comes from `[[input]+0x30]+8` minus `0xC39E0(note time)`. `0x9FDF0` is the judging call made when a note times out (late bound +0xA0/+0xA4 compared there).
