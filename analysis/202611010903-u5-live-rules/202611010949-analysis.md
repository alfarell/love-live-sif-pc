# U5 remainder: score multiplier and hold ticks

Created: 202611010949 (Asia/Jakarta). Follows `202611010917-analysis.md`. Addresses are in `work/elf/eboot.elf` (Ghidra, image base 0). The decompiled files are in the session scratchpad and are not committed.

## 1. The live context's second pointer is `s_CommonParam`

The score and tick functions read `ctx[1] + offset`. Every offset they use holds a fitting value in `s_CommonParam` (`live_params.bin`):

| Offset | Value | Used by |
|---|---|---|
| +0xB4 | 100 | base points (0xAA520, 0xA9D80) |
| +0xBC + grade × 4 | 0.1 / 0.2 / 0.7 / 1.0 | weights (Bad … Perfect) |
| +0x120 | 3.0 | skill score multiplier (when `0x93D00` is true) |
| +0x128, +0x12C | 0.033 | tick fraction (normal, skill) |
| +0x130 | 0.041667 (1/24 s) | tick length |
| +0x1B4/+0x1B8/+0x1BC | 2000 / 6000 / 30000 | per-note-flag bonus counters (0xAA270; flags 0x800/0x1000/0x2000) |
| +0x1A0, +0x1A4 | 9, 9 | *Hypothesis:* caps |

The score code also gets the same table directly: `0x946A0` returns its address.

## 2. The "combo multiplier" is a difficulty multiplier

- `0xCA910(CommonParam, rec)` returns `CommonParam[+0xD0 + clamp(rec[+0x14], 0, 8) × 4]`.
- `rec` is set in `0xA9480`. That function calls `0x945B0(id)`, which does a linear search over 904-byte records keyed by their first int.
- Only one table has 904-byte records: `s_live_datas` in `common/common.pac/live_common.pac/live_datas.bin` (1,125 records).

The first fields of each record:

| Offset | Content |
|---|---|
| +0x00 | id = song × 1000 + variant (10000, 10001, …, 10013) |
| +0x04 | song id |
| +0x08 | variant (0–4, 10–13) |
| +0x0C | 100 |
| +0x14 | **difficulty index 0–8** (variants 0–4 → 0–4, 10–13 → 5–8; 125 records each) |
| +0x18 | *Hypothesis:* star level (2, 4, 5, 6, 11 for song 0010) |

The multiplier is therefore fixed for each chart and does not depend on the combo. `+0xD0` holds 1.0, 1.5, 2.0, 2.5, 3.0 for ac_easy … ac_challenge, then 1.5, 2.0, 2.5, 3.0 for cs_basic … cs_master. The record also confirms the variant order given in `song.h`.

## 3. Hold ticks (`0x9ECC0`, `0xA9D80`)

1. **Press** (state 1, start-hold set):
   - The game stores the press time (+0x6C).
   - Tick count (+0x68) = round(hold length / (int)(0.041667 × 1000)), that is, round(length / 41 ms). The int cast truncates 41.67 to 41.
2. **Held** (state 2, checked every frame while the time is ≤ the note end):
   - One tick each time (now − press) − (ticks given + 1) × 41 > 0, up to the tick count.
   - Each tick calls the listener at vtable +8. That listener goes through 0xAA140/… to `0xA9D80`, with a count of 1.
3. **Release:**
   - The record overwrites the note's grade (+0x4C) with the release grade.
   - On a Perfect or Great release, the remaining ticks go to listener +0x10 → `0xA9D80` with count = remaining.
   - Remaining ticks are therefore scored at the release grade, and ticks given while held at the press grade.
4. **Points** (`0xA9D80`):
   - Formula: `round(difficulty multiplier × 0.033 × weight[note grade] × 100) × count`. Rounding is half away from zero (sign × floor(|x| + 0.5)). The total is capped at 9,999,999.
   - Ticks add score only. They do not touch combo or the grade counts. `0xAA270` (the grade counter) is not on the tick path.
   - Per tick at multiplier 1.0: Perfect 3, Great 2, Good 1, Bad 0.

**Skill path:** with the skill check (`0x93D00`) true, the fraction is +0x12C, also 0.033. In `0xAA520` the skill multiplier is +0x120 = 3.0.

## 4. Check against the shadPS4 runs

Song 0340 ac_easy has 101 notes, 20 holds and 569 ticks; `sif_live_test` gives an all-Perfect autoplay score of 13,807. The shadPS4 runs scored above the base formula by +27 (edges run), +54 (per-lane run) and +426 (the +80 ms run, mostly Good, ≤ 1 point per tick). All three fit inside the 569 tick points available. Without a per-note log of those runs this is consistent, not proven.

## 5. Applied in the port

- `ScoreRules` (`judge.h`) holds the multiplier, the tick fraction and the tick length. `LoadScoreRules` (`song.cpp`) reads them from `s_live_datas` and `s_CommonParam`.
- `Judge` scores ticks as described in §3. One difference: the port clamps the tick time to the note end, so a late `Update` still gives the ticks that per-frame updates would have given.
- New tests in `live_test.cpp`:
  - 24 ticks × 3 points on a 1000 ms hold;
  - multiplier 3.0 → 300 points per note and 10 per tick;
  - a hold let go at 600 ms gets 14 ticks;
  - song 0010/04 loads multiplier 3.0.
- The real song 0010/04 all-Perfect score is now 199,220.
