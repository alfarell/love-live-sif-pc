## 1. SELF headers and encryption

Read with `struct` from the first 0x400 bytes of each file (header layout: `pt-pc/docs/formats/self.md:7-31`):

| File | SELF header (ver/mode/endian/attr) | header size | segments | segment flags (low 20 bits) | Result |
|---|---|---:|---:|---|---|
| `eboot.bin` | 00 01 01 12 | 0x480 | 10 | `0x10004`, `0x2804` | plaintext |
| `sce_module/libc.prx` | 00 01 01 12 | 0x440 | 10 | `0x10004`, `0x2804` | plaintext |
| `sce_module/libSceFios2.prx` | 00 01 01 12 | 0x3D0 | 8 | `0x10004`, `0x2804` | plaintext |
| `sce_module/libSceNpToolkit2.prx` | 00 01 01 12 | 0x3D0 | 8 | `0x10004`, `0x2804` | plaintext |
| `sce_sys/about/right.sprx` | 00 01 01 12 | 0x360 | 8 | `0x10006`, `0x2806` | **encrypted** (bit 0x2) |

Flag bits per `pt-pc/docs/formats/self.md:23-24`: 0x4 signed, 0x2 encrypted, 0x800 blocked. So the eboot and the three game modules are **fake-signed SELFs with plaintext segments**, exactly like P.T. (`pt-pc/docs/formats/self.md:27-28`). `self2elf.py` converted all four; it refused `right.sprx` ("segment 0 is encrypted"). `right.sprx` is a system "about" (copyright notice) module, not game code (Hypothesis from its path); the port does not need it.

## 2. eboot ELF layout

`self2elf.py` output for `eboot.bin` (11,117,753 bytes → 11,118,585-byte ELF):

| # | type | file off | vaddr | file size | mem size |
|---|---|---|---|---|---|

| 2 | LOAD (data/bss) | 0xA48000 | 0xE00000 | 0x2A30 | 0xFCC30 |
| 3 | SCE_PROCPARAM | inside #2 | 0xE00000 | 0x60 | |

| 5 | INTERP | inside #0 | | 0x15 | |
| 6 | TLS | | | 0 | 0 |
| 7 | GNU_EH_FRAME | | 0x9F45EC | 0x2B49C | |

| 9 | SCE_COMMENT | | | 0x4C | |
| 10 | SCE_VERSION | | | 0x65D, no data in SELF (zero-filled, as in P.T.) | |

- `e_type` = **0xFE10** (ET_SCE_DYNEXEC: position-independent executable). P.T.'s eboot is 0xFE00, fixed at 0x400000 (`pt-pc/docs/formats/self.md:39`). So a loader for SIF must relocate the eboot (11,565 `R_X86_64_RELATIVE` + 222 `R_X86_64_64` relocations, `dynlib.py` summary).
- `e_machine` 0x3E (x86-64); **entry point `0x295750`** (image-relative).
- `SCE_PROCPARAM`: size 0x60, magic `ORBI`, version 5, SDK field `0x05050001` (fits `sdk_ver=05050000` in `param.sfo` `PUBTOOLINFO`, Part 2).
- `SCE_COMMENT` / `original_filename`: `F:/lp5_home/svn/lp5_master/obj/lp5/ORBIS/Release_Dll/lp5.elf`. The project's internal name is **"lp5"**, built from an SVN tree; "ORBIS" is the PS4 SDK platform name. The `Release_Dll` configuration name is a Hypothesis hint that the engine also builds as a DLL elsewhere (PC arcade build?).
- No TLS segment in the eboot (size 0); `init` 0x20, `fini` 0x5DDC10, empty init/fini arrays (`dynlib.py` summary line).
- Code size: the r-x LOAD is 10.6 MB (code + read-only data), about 40% of P.T.'s 0x177C6E0 = 24.6 MB (`pt-pc/docs/formats/self.md:43`).

The three PRX files are `ET_SCE_DYNLIB` (0xFE18), entry 0, with `SCE_MODULE_PARAM`; original file names point to Sony build paths (`W:/Build/J02410092/sys/internal/usermode/src/libc/...`, `.../fios2/libSceFios2.prx`, `W:/Build/J02410110/opt/internal/np_toolkit_v2/lib/libSceNpToolkit2.prx`), so they are **Sony SDK libraries shipped with the game**, not game code.

## 3. Modules and imports

### Naming the NIDs

A **NID** is the 11-character ID a PS4 executable uses instead of a function name: the first 8 bytes of SHA-1(name + fixed suffix), base64-encoded (`repository/tools/dynlib.py` `name_to_nid`, from pt-pc). Without a NID database, names can only be recovered by hashing candidate names. Candidates: all identifier-like strings in the four ELFs plus all identifiers in the local w64devkit C/C++ headers (596,773 candidates, `work/candidate-names.txt`, local only). Result:

| Module | Imports | Named | Exports |
|---|---:|---:|---:|
| `eboot` (lp5) | 559 | 124 | 0 |
| `libc.prx` | 109 | 45 | 2,565 |
| `libSceFios2.prx` | 81 | 47 | 168 |
| `libSceNpToolkit2.prx` | 279 | 42 | 2,727 |

A full NID database (for example the one used by shadPS4 or "ps4libdoc"; `pt-pc/tools/dynlib.py:126` mentions GhidraOrbis `nid_db.xml` or shadPS4 sources) would name the rest. Not available in our folders (Open questions).

Observations:

- **Only 559 imports in total.** The engine uses few system functions; middleware (CRI, Iggy, see section 4) must be statically linked into the eboot.
- Named kernel imports are plain file and thread calls: `sceKernelOpen/Read/Write/Lseek/Close/Stat/Fstat/Fsync/Ftruncate/Mkdir`, `scePthreadCreate/Join/Mutex*/Cond*/Attr*/Setaffinity/Setprio/Rename`, `sceKernelCheckReachability`. Named libc imports are standard C (`malloc`, `fread`, `sprintf`, math, `setjmp/longjmp`, `__cxa_*`).
- **Audio:** `sceAudioOutInit/Open/Output/Outputs/Close` only. No `libSceAjm` (hardware audio decoding) and no `libSceNgs2` (Sony mixer). So decoding and mixing are done in software inside the eboot (consistent with CRI ADX2), and the output is plain PCM through AudioOut. That is the easiest audio case for a port.
- **File access:** the eboot itself imports `sceKernelOpen/Read/...` and **no `libSceFios2`**; `libSceFios2.prx` is a dependency of `libc.prx` (`libc` imports 11 Fios2 functions, `dynlib.py` output). Hypothesis: the game reads its files through plain kernel/libc calls.
- **Graphics:** 87 `libSceGnmDriver` + 13 `libSceVideoOut` imports, all unnamed so far.
- **Online:** 181 NpToolkit2 + 9 NpManager + NetCtl, Trophy, GameLiveStreaming, SharePlay, ScreenShot, VideoRecording, friend list dialog (section 7).

## 5. Where the game logic lives

- **Native C++ in the eboot.** Evidence:
  - Game flow "sequences" `sqBoot`, `sqDebugBoot`, `sqTitle`, `sqTopMenu`, `sqGame`, `sqFx`.
  - Gameplay components (16), for example `ComponentNote`, `ComponentNoteExact`, `ComponentNoteLongConnector`, `ComponentJudgeRing`, `ComponentCombo`, `ComponentEvaluation`, `ComponentLiveTimer`, `ComponentIngameBeatLine`, `ComponentIngameResult`.
  - Test processes (12), for example `ProcessTestScorePlayer`, `ProcessTestMovie`, `ProcessTestFlash`, `ProcessTestShadow`, `ProcessTestDlcSound`.
  - No script VM (section 4).
- **Data-driven by master tables.**
  - About 59 `*.bin` table names: `live_datas.bin`, `live_params.bin`, `character_params.bin`, `dress_data.bin`, `item_data.bin`, `award_master.bin`, `level_datas.bin`, `dlc_music_data.bin`, `dlc_dress_data.bin`, `dlc_set_data.bin`, and others.
  - Archive names: `data.pac`, `game.pac`, `sif.pac`, `dlc.pac`, `score.pac`, `timeline.pac`, `scene.pac`, `layout.pac`, `mission.pac`, `reward.pac`.
  - Note charts are the `score.pac` in each song folder (`live/NNNN/NNNN.pac`, Part 2 section 4).
- **Size.**
  - The eboot's `.eh_frame_hdr` table lists **19,807 functions**. The FDE count was read at file offset 0x9F85EC + 8, with the encoding checked as `udata4`. This count includes CRI, Bullet, libjpeg, zlib and FreeType.
  - The eboot's r-x segment is 10.6 MB.
  - For comparison, P.T.'s eboot has **68,426** functions (same method, offset 0x15D16E4) and a 24.6 MB r-x segment. pt-pc needed ~42k lines of C++ game code plus the game's own Lua scripts (`pt-pc/docs/lua_api.md`) for P.T. (Part 1, section 6).
  - Hypothesis: SIF's own game-specific code is a few thousand functions. Without symbols, a rewrite would have to reverse-engineer all of it.

## 6. Graphics and shaders

- **Imports:** 87 from `libSceGnmDriver` and 13 from `libSceVideoOut`; names unresolved (section 3).
- **No `libSceGnmx` module.** The shader-loader error texts (`Error: shaderBinarySize %u is not sufficient to hold sizeof(Header) ... Header::m_codeSize ... sizeof(Footer)`) suggest GNMX-style helpers are statically linked (Hypothesis).
- **Shaders are precompiled PS4 GCN binaries:**
  - The marker `OrbShdr` occurs **806 times in the eboot** and **26,196 times in `shader/ps4/sh_custom.pac`**.
  - The eboot's first match reads `4f 72 62 53 68 64 72 07 ...`, which is `OrbShdr` followed by version 7.
  - This is the `ShaderBinaryInfo` footer pt-pc documents for P.T. ("`OrbShdr`, version 7", `pt-pc/docs/formats/fsop.md:78`). So SIF uses the same PS4 shader-binary format as P.T., and pt-pc's GCN tools (`tools/gcn.py`, `tools/gcnexpr.py`) apply in principle.
- **The shader archive:** `sh_custom.pac` is an `ARC` with 9 top-level entries (header u16 at 0x06). Entry tags in its first table include `SHG\0`, `bin\0` and `ARC\0` (Hypothesis: shader groups). `BlShaderArchive` is the eboot's class for it.
- **Other renderer hints:** `ssaoUvOffset` (SSAO), `ProcessTestShadow`, `ProcessTestMorph`, `vertexes(unified)`.
- **Video:** CRI Sofdec2 decodes `.usm` (`criVdec/PS4`, `CRI MPV/PS4`), and there is no `libSceVideodec` import. Hypothesis: decoding runs in software on the CPU and frames are uploaded as textures.

- **Only format-level checks found:**
  - CRI CPK CRC checks (`CPK Analyzer::CRC Error in TOC`, `EnableTocCrc`, `EnableFileCrc`).
  - `header crc mismatch`, `E2010052905:Integrity violation`, `E2015042403:Decryption failure.` (CRI error-code style).
- **No anti-debug or jailbreak strings:** searches for `ptrace`, `debugger`, `jailbreak` and `tamper` found nothing relevant. The `RSA`/`AES` hits are font glyph names.
- **Audio encryption:**
  - The HCA streams in `sound/music.awb`, `sound/voice.awb` and `sound/dlc/MUSIC_0010.awb` have plain `HCA\0` headers (2, 78 and 1 in the first 4 MB), and their `ciph` type is `0000`, i.e. not encrypted.
  - No masked headers (`C8 C3 C1 00`) were found.
  - Sampled only the first 4 MB of three files.
- **Conclusion (Hypothesis):** no anti-tamper beyond CRCs. Not proven without disassembly.

## 10. Engine verdict

**SIF ("lp5") is a native C++ game on an in-house engine.** It was built from the arcade game's code base (NESiCA strings) for PS4 SDK 5.05. It is not Unity, Unreal, Cocos or Fox Engine.

- **Middleware, statically linked:** CRI ADX2 (HCA audio), CRI Sofdec2 (USM video), CRI FS, Bullet, zlib, libjpeg, probably FreeType, and a Flash-based UI ("Gfx" classes, `.iggy` files).
- **Game logic:** native code in the eboot (`sq*` sequences, `Component*` classes), driven by binary master tables and `ARC` archives. There is no script layer to reuse.
- **System surface:** the eboot is fake-signed, plaintext and position-independent (ET_SCE_DYNEXEC), with **only 559 system imports**:
  - audio is plain AudioOut PCM (no Ajm, no Ngs2);
  - file I/O is plain kernel calls;
  - graphics are 87 GNM imports plus precompiled GCN shaders (`OrbShdr` v7, about 27,000 binaries).

**First hint for Part 8 (Hypothesis):**

- **A pt-pc-style rewrite** would mean reverse-engineering all game logic from about 20k native functions, with no symbols and no scripts. That is much harder than P.T., whose logic was partly Lua and well documented.
- **Emulation/HLE (option B) or a hybrid (option C)** looks more attractive. The eboot is plaintext x86-64, and its system surface is small and mostly easy: kernel, libc, AudioOut, Pad, SaveData, and stubs for Np/store. The big cost is **GNM command translation and GCN shader translation**.
- **Reuse from pt-pc:** its offline GCN tools and shader-format knowledge matter for B/C. Its runtime code does not.
