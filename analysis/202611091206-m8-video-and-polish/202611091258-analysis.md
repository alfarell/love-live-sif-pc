## 1. Monitor video path (eboot `0xBD4C0`)

The eboot strings are at file offsets; the first ELF segment maps file `0x4000` to address 0, so `movie/monitor_%03d.usm` is at `0x5E9290` and `movie/monitor_%03d_%c.usm` at `0x5E9276`.

Only `0xBD4C0` loads them. It builds the path into a string and sets `[this+0xD0] = 1` (loaded):

| Part | Source in the code |
|---|---|
| `%03d` | `[[[arg2]] + 0xA0] + 0x16C`: a field of a **run-time object**. It is not in `s_music_datas` (floats there), `s_live_datas` (always 0) or `s_stage_datas` (records are only 0x148 bytes) |
| `_%c` | `'a' + byte +0x2F` of the record returned by `0x23B8B0(id at [this+0x78]+0x228)`. When the byte is 0, the name has no letter |

Byte `+0x2F` of `s_stage_datas` (`common/common.pac/stage_common.pac/stage_datas.bin`, 0x148-byte records) is **1 only for stage 6** and 0 for every other stage. *Hypothesis:* `0x23B8B0` is the stage lookup, so only stage 6 plays the `_b` videos.
- **Fits:** stage 6's model has a single plain `monitor` / `monitor_mesh` and no dot mask, unlike the others.
- **Does not fit:** `_b` files exist for 001-007 and 051, so the number must still vary on stage 6.

The stage-logo names `monitor_logo_%02d(_%c)` (`ui/ui_monitor.pac`, logos 00-03 plus `_b`) are chosen the same way, at `0xBD3A7`-`0xBD429`, from field `+0xD8`.

**Not found statically:** where the number comes from. The code at `0xB6991` and `0x23C7B8` that writes `+0x16C` belongs to other structs (camera floats, flags). Tracing the run-time object would take a debugger or a long decompile; a game run can show it directly.
