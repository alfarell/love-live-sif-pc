# M4 follow-up: judgement sweep in shadPS4

Created: 202611010048 (Asia/Jakarta). Follows `202611010004-analysis.md`. User decision: "Judgement sweep". Every run used the isolated `work/shadps4-run/user` folder; `%APPDATA%\shadPS4` stayed untouched (newest file still 2026-10-31 23:54:51).

## 1. Tool: `sif_sweep` (`repository/src/tools/sweep.cpp`)

- Loads the chart and decodes the same music cue through the port's own code, as a mono 4 kHz reference.
- Captures the system audio with WASAPI loopback (here 192 kHz float). Every packet carries the QPC time of its first frame.
- Finds the song by normalized cross-correlation with a 1.5 s piece of the reference, then keeps searching 100 ms past the first hit above 0.8 and takes the best lag. This gives the QPC time of audio sample 0 at 0.25 ms resolution. Correlation reached 0.999 on shadPS4 and 0.964 on the port.
- Presses and releases lane keys with `SendInput` at sample 0 + note audio time + offset. Timer resolution is set to 1 ms, the last 20 ms are spin-waited, and events at the same instant go out back to back. Measured lateness: mean 0.15 ms, max 0.42 ms.
- Diagnostics: `--lane-offset LANE:MS`, `--skip-lane LANE`, `--tap-only`. Key maps: shadPS4 default (E Q ← ↓ → N B U O) or the port's.

## 3. Rule findings

- **Five grades: Perfect, Great, Good, BAD, Miss** (result screen). The four bounds of `s_EvaluateRangeDatas` are Perfect / Great / Good / Bad; outside them a note is a Miss. The judge was corrected (`Grade::Bad`, `kBounds = 4`); tests updated.
- In the per-lane run (`--lane-offset` −75/−160/−240/−310 ms for lanes ←/↓/→/×), every hit of each lane landed in exactly one grade: Perfect, Great, Good and Bad in turn. This matches the table's ±40/133/200/267 bands at the offsets chosen.
- **Judgement count differs from notes + holds:** song 0340 Easy has 101 notes and 20 holds (121), yet the result screen totals 128 (no input) or 132 (with input). Unexplained; tracked under U5.

## 5. Results

- **Centre in shadPS4:** relative to the audio in the system mix, the game's Perfect centre is at **c ≈ −100 … −88 ms** (players must press about 90 ms before they hear the beat). Runs 2, 3 and 5–7 bound it; runs 5–7 are identical, so the edges could not be resolved further.
- **Time steps:** shifting the presses by 8–12 ms changed nothing in runs 5–7. The game evaluates input per frame. At 100 BPM every note falls on the same frame phase (300 ms = 18 frames at 60 fps), so all notes cross a boundary together: the measurement moves in frame-sized steps.
- **Dropped presses in shadPS4:** about half of the presses never count (the → lane in run 4 was the exception, 17/17). The losses repeat exactly across runs, so they are systematic: probably short taps or simultaneous keys through shadPS4's keyboard-to-pad path, not timing. This does not affect the grade of presses that do count.
- **What c contains:** c = the game's own timing − shadPS4's audio output delay. shadPS4 queues guest audio in an SDL stream (up to 4× the guest buffer before it clears the queue, `src/core/libraries/audio/sdl_audio_out.cpp:38`, `:497`), plus the Windows device period. Without real PS4 hardware the two parts cannot be separated. So **shadPS4 cannot give the game's absolute audio offset**; it does confirm the judgement *rules* (windows, grades, lane mapping).
- **Port, same tool:** presses at loopback audio time register in `sif.exe` at **+18.0 ms** (SD 4.2 ms, 4 hits). The port's `PlayheadMs` therefore runs about 18 ms ahead of the system mix: one Windows shared-mode period (10 ms) plus SDL's stream buffer is not subtracted. This is the port's own constant, independent of the game.

## 6. Conclusion for M4 "timing parity"

- Rule parity is confirmed: the same windows (ms), five grades, lane order.
- Absolute parity against the console is not measurable with shadPS4 (emulator audio delay), and absolute offset depends on each machine's audio and display delay anyway. The game itself exposes a "Judgment Timing Adjustment" setting (`s_UserCalibrationData`, −80…+80 ms). The port has `--calibrate`.
- Proposed: close the M4 timing item as "rule parity verified, absolute offset per-machine calibration". In addition, correct the port's clock by the measured shared-mode delay so that offset 0 means "on the beat as heard through the system mix". Both need the user's agreement (it changes the M4 exit criterion).
