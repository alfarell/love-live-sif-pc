## 4. The `.pac` container (first look, Hypothesis)

Short header dumps (`od -t x1z`) of `CUSA24620/sandbox/viewer/viewer.pac` and `CUSA24620/live/0010/0010.pac`:

```
viewer.pac  00: 41 52 43 00 00 01 01 00 01 00 00 00 00 00 00 00  ARC.............
            10: "viewer.pac" padded to 0x30
            30: 80 00 00 00 ...
            40: 62 69 6e 00 00 00 00 00 c2 3a 77 95 00 00 12 00  bin......:w.....
            50: 00 00 00 00 "viewer_params.bin" ...
            80: b8 07 00 00 80 00 00 00
0010.pac    00: 41 52 43 00 00 01 03 00 03 00 00 00 00 00 00 00
            10: "0010.pac"
            40: "scds" 00 00 00 00 19 8e 1f 24 00 00 0a 00 00 00 00 00 "score.pac"
            60: "scn"  00 00 00 01 00 fb b3 ab 18 00 00 0a 00 00 00 00 00 "scene.pac"
            80: "btls" 00 00 02 00 20 25 cd db 00 00 0d 00 00 00 00 00 "timeline.pac"
```

Hypothesis on the layout: `ARC\0`, u16 = 0x0100 (version?), u16 entry count (repeated), then the archive's own name; a table of entries each with a 4-byte type tag (`bin`, `scds` = score, `scn` = scene, `btls` = timeline), an index, a 32-bit value that looks like a name hash, a name length, and the **plain-text entry name**. So archive contents are **named and not encrypted** at the table level, and archives nest (`0010.pac` holds `score.pac`, `scene.pac`, `timeline.pac`). Entry counts from the header (8-byte heads, `by_magic4`): 1 entry (1,788 files), 3 (761), 2 (726), 5 (83), 10 (49), 4 (48), 7 (32), 0x14 = 20 (4).

`cmp\0` wrapper (`ui2/95_result_en.pac`): `63 6d 70 00` `7a 6c 69 62` ("zlib") `07 da 33 00` (0x0033DA07 = 3,398,151 = file size 3,398,167 − 16, so compressed size) `80 41 d3 00` (0x00D34180 = 13,844,864, so uncompressed size), then a zlib stream (`78 9c`). `common/common.pac` uses `lzma` the same way.

Both need a proper parser in Part 3 or a later tooling part. Not done here (no extraction in this part).

The game files themselves are inside the encrypted PFS, so a file-by-file comparison of dump vs PKG is not possible without decrypting the PFS (not done, see below). The size gap (PKG 11.6 GB vs dump 23.4 GB) fits a compressed inner image (PFSC, as in `pt-pc/docs/formats/pkg.md:84`). Hypothesis.

### Fake PKG or store PKG?

**Not decided; blocked by policy, not by tools.** The definitive test described by pt-pc (`pt-pc/docs/formats/pkg.md:60-67`) is whether `image_key` decrypts with the public **fake** keyset; retail packages fail that check. Doing that needs key material inside our scripts, and our rules forbid storing keys. Indicators only:

- `pkg_type` `0x40000001`, `content_flags` `0x0A000000` and `pfs_image_flags` high bits `0xA0...` differ from pt-pc's retail example (`0x81000001`, `0x02000000`, `0x80...`). Hypothesis: this points to a package rebuilt by a packaging tool (fake PKG), not a PSN store download. Unverified; one retail sample is not enough to judge.
- The existence of a full dump (`CUSA24620/`) plus `Extracted/` DLC folders suggests the user extracted the packages, which only works for fake PKGs (pt-pc README: store PKGs are "encrypted for the console that owns it", `pt-pc/README.md:39-40`). Hypothesis.

What matters for the port: **the dump folder `CUSA24620/` is complete and readable**, so the port does not need to read the PKG, the same way pt-pc accepts dump folders (`pt-pc/docs/installer.md:67-77`). The question only matters for an installer that takes PKGs. Recorded in Open questions.

## 7. DLC: the 63 "1 MiB" vs 117 larger PKGs

`ps4_meta.py pkgdir DLC/` → `sif-pkg-dlc.json`; `Extracted/` census → `sif-census-extracted.json`.

- File names: the 180 PKGs are **two families**, not one: `LLSIFACHMCOS0001`..`COS1024` (63, **costumes**) and `LLSIFACHMMUS0001`..`MUS1049` (117, **music**). Part 0's listing (`ls | head`) showed only COS names. (IDs are not contiguous.)
- All 180: `pkg_type 0x1`, `content_type 0x1B`, `content_flags 0x0A000000`, one PFS image, PFS mode `0x0D`, `param.sfo` `CATEGORY ac` (additional content), `VERSION 01.00`, content IDs `JP0082-CUSA24620_00-LLSIFACHM{COS|MUS}NNNN`, titles are song or costume names (for example COS0001 「Bokura no LIVE Kimi to no LIFE」, COS1024 「Live T-Shirt」, MUS0002 「Yujo No-Change」, MUS1049 「RED GEM WINK」).
- Entry tables are identical in shape: metadata entries + `0400`, `0401`, `0409`, `param.sfo`, `icon0.png`.
- Size: every COS PKG is exactly 1,048,576 bytes with a PFS image of `0x80000` (512 KiB); MUS PKGs carry PFS images of 4 to 6 MiB.
- `Extracted/`: COS folders hold only `sce_sys/` (5 files: `icon0.png`, `license.dat`, `license.info`, `param.sfo` 972 bytes, `psreserved.dat`); MUS folders hold the same plus **one `MUSIC_NNNN.awb`** at the folder root.
- So COS DLC are **pure entitlements** (unlock flags; the costume data must already be in the base game, presumably `chr/cNN/dNNN/dNNN.pac`, Hypothesis), and MUS DLC carry one CRI AWB music file each.

## 9. Engine and middleware hints from the file tree (all Hypothesis until Part 3)

- **CRI Middleware:** `.awb` with `AFS2` (ADX2 audio wave banks) and `.usm` with `CRID` (Sofdec2 video). No `.acb` cue sheets seen in the tree; Hypothesis: cue data is inside `sound/sound.pac`.
- **Iggy / Flash UI:** `.iggy` files (`sd_chr/*/sd_character.iggy`), Flash `.swf` tests and an `.fdt` in `sandbox/swf_test/`. Iggy is a Flash-based UI runtime from RAD Game Tools; Hypothesis.
- **Own archive format `ARC\0` (.pac)** with typed, named entries and `cmp\0` zlib/LZMA wrappers. Not PSARC, not Fox QAR/FPK, not Unity (`UnityFS`/`.assets`/`globalgamemanagers`), not Cocos (no `.lua`/`.luac`/`.plist`), not Unreal (`.pak` with Unreal footer, `.uasset`). So **not Unity, Unreal, or Fox Engine**; likely an in-house engine (Hypothesis). The arcade original ran on arcade PC hardware (Hypothesis from general knowledge; check strings in Part 3).
- **Shaders:** `shader/ps4/sh_custom.pac` (100 MB) and `shader/common_shader_tex.pac`, a `ps4/` subfolder suggests per-platform shader builds; Hypothesis: compiled PS4 shaders (GNM/PSSL binaries) inside ARC.
- **Rhythm-game data:** per-song folders `live/NNNN/` with `score.pac` (tag `scds`), `scene.pac` (`scn`), `timeline.pac` (`btls`), plus `sandbox/sample.scd` with magic `Scor`. These are the note charts and stage timelines.
- **Characters:** `chr/c01`..`c09` (9 members) and `c11`..`c19` (9 more), `c21`, `c22` (2 more) fit the two idol groups μ's and Aqours plus two extra characters (Hypothesis).
- **Localization:** `_cn`, `_en`, `_tw` variants beside base (Japanese) files in `ui/`, `ui2/`, `effect/`, `proca_preset/`.
- **Developer leftovers** in `sandbox/` (`bscam`, `canm` "FBXA", `scd`, `btx`, viewer): useful for format study.

## 10. What pt-pc expects from a dump, and whether SIF matches

- pt-pc recognises its game by content: a PSARC + a QAR and `pt14_` level names or a known title ID (`pt-pc/docs/installer.md:79-94`); it copies three archives and ignores eboot, `sce_module`, `sce_sys` (`pt-pc/README.md:54-56`).
- SIF has none of those archives; its data is ~3,550 `ARC`/`cmp` `.pac` files plus CRI `.awb`/`.usm`. **None of pt-pc's format readers apply** (they are Fox Engine formats, Part 1 section 5).
- What does carry over: the policy (dump folder or fake PKG only), recognition by content plus title ID (`CUSA24620` from `sce_sys/param.sfo`), and reading data in place at run time.
- A SIF port would likely need the whole `CUSA24620/` tree (about 21.8 GiB of data), not a few archives.
