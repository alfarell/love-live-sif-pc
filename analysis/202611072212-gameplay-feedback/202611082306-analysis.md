### Audio: `sound/sound.pac/sys.acb`

`sys.acb` is a CRI ADX2 **cue sheet**: a table of named sounds ("cues"), each built from tracks that play waveforms stored in the sheet's own wave bank. It has 296 cues and 286 waveforms. The cues were resolved with a scratch script that uses `tools/acb_dump.py`'s reader.

The path a cue resolves through is: cue → sequence → tracks → note-on event → synth → waveform.

| Cue (index, CueId) | Name (meaning) | Waveforms (MemoryAwbId, seconds) |
|---|---|---|
| 25, 20030 | `Perfect` | 184 (1.0), 249 (0.34), **46** (1.52) |
| 26, 20031 | `Great` | 80 (1.0), 248 (0.45), **46** |
| 27, 20032 | `Good` | 79 (1.0), 247 (0.56), **46** |
| 28, 20033 | `Bad` | 76 (1.0), 246 (0.45), **46** |
| 29, 20034 | `miss` | 204 (1.0) |
| 32-36, 20039-20043 | `Perfect_fl` … `miss_fl` (finale) | The same layers plus **195** (4.0 s) |
| 81-85, 21030-21034 | `判定：PERFECT` … `判定：MISS` (判定 = "judgement") | The same waves as 25-28. MISS adds 74 (0.12 s). |
| 88-92 | `フィナーレ判定：…` (finale judgement) | Like `_fl` |
| 111-120 | `特殊譜面用：…` ("for special charts") | Variants |

All judgement sequences have `Type` 0. In public CRI knowledge, type 0 is **polyphonic**: every track plays at once (*Hypothesis*). Some tracks carry track commands (`CommandIndex` ≠ 0) that were not decoded. They may set volume or delay.

### Which cues the game plays (eboot)

The function at eboot `0xB06C0` reads the grade from field `+0x4C` (0 Miss, 1 Bad, 2 Good, 3 Great, 4 Perfect; the reverse of the port's enum). It looks up a CueId in one of two tables of `[grade][column]` pairs and tail-calls `0x229C30` (169 call sites, so most likely the generic "play sound effect by cue ID" function).

- **`0x5E8BA0`, the normal table:**
  - column 0: miss 20034, Bad 20033, Good 20032, Great 20031, Perfect 20030, i.e. cues **25-29**;
  - column 1: the `_fl` finale cues 20039-20043.
- **`0x5E8B70`:** used only when note flag `0x1800000` is set (*Hypothesis:* special charts). It holds 21032-21034 and the 特殊譜面用 cues 21141-21150. If its entry is 0, the code falls back to the normal table.
- **Column:** column 1 is chosen when `[ctx+0x60]+8 == 4`. *Hypothesis:* the live is in its finale section, from the `_fl` names.
- **Mash cue:** a Perfect on a note with flag `0x100000` and `+0x70 > 1` plays 21100 instead (*Hypothesis:* a mash or multi-press note; the port's charts have no such type yet).
- **Callers:** `0xB06C0` has no direct call. It is reached through a function pointer, so who calls it per judgement (press and release) is not traced.

**Answer to "about three sounds":** the game has **five** judgement cues, and each grade has its own two layers. Perfect, Great, Good and Bad share layer 46 (1.5 s, probably the common tap sound), and Miss has none of it. By ear these may group into fewer sounds, but nobody has listened to them yet. Decoding them to WAV under `work/` for a listening check is part of the plan.

## 3. Comparison against the references

### Item 1: note size and bracket spacing

The game's frames and the port's captures were measured at the same 1280 × 720 scale. Images 2-4 are video stills of unknown scale, so only ratios within one image are used.

| Measure | Game | Port |
|---|---|---|
| Indicator orange ring (1280 frames) | 116 px (`0100_026224.jpg`) | 116 px (`g3_port_held_c.png`): identical, so the 1:1 indicator is right |
| Note ring at the indicator ÷ indicator ring | 0.87 (image 4, held ↓) to 0.93 (image 3, ← at the hit) | **0.80** (143 / 177, by construction) |
| Bracket span ÷ ring, held | 1.22 (image 4) | 1.42 (1.21 × 1.17) |
| Bracket span ÷ ring, in flight | 1.41 (G4, frame `0100`), 1.46 (image 2) | 1.42 (1.50 measured in image 1) |
| Gap between the bracket's inner edge and the ring, ÷ ring | about 0.10 (image 2) | about 0.06 (image 1) |

**Finding:** the game's note ring at arrival is about **9-16% larger** than the port's, which agrees with the user's report. The bracket results disagree between states: 1.22 held, 1.41-1.46 in flight. Either the bracket scales differently from the note, or a held note is drawn larger in the game. With the stills available this cannot be settled. **Uncertain:** the measurements are by eye on zoomed crops, about ±3 px.

*Interpretation:* the request says the brackets sit "too tightly against each other". It is read here as the bracket hugging its own note: the gap is smaller in the port. In image 1 no two different pairs touch.

### Item 2: end cap

- **Game** (image 3, frame `0082_021504`): a solid white disc with a sharp edge, as wide as the band at the tail.
- **Port:** `circle_05`'s glow dominates. At the tail near the centre the note size is small (0.2-0.4 × `kNoteSize`), so the 110 px core shrinks to a few pixels and only the halo shows. The result looks blurry, and pink while held.

**Cause:** the wrong asset, not filtering or blending.

### Item 3: hold brackets

Image 4 (game, a held ↓ × pair): the heads on the rings have **orange** brackets, and both tails near the top have **blue** brackets around their end caps. The port draws no brackets at tails.

**Colour rule.** Two rules were compared against the user's table and the existing tap alternation.
- **Rule A (recommended):** number every simultaneous **event** in time order. An event is a group of heads at one time, or a group of hold tails at one time. The colour is the event number % 2.
  - For hold pairs that do not overlap, this gives head orange / tail blue for every group, exactly the user's table.
  - For tap pairs, it gives orange, blue, orange…, as now.
- **Rule B:** the colour is the group number % 2 and the tails take the opposite. It contradicts the table: the second group would start blue.

**Uncertain:**
- the colours when another simultaneous event falls between a group's heads and its tails;
- whether two holds that start together but end at different times get tail brackets;
- whether a hold tail at the same time as another note's head counts as one event.

No game frame of these cases was found.

### Item 4: layering

The port draws notes and bands after `center_mic`, the gauge fan and the HUD's `uip0006_Songgage`, so they cover the mic. In the game's frames, notes come out from under the mic.

**Fix:** draw the bands and notes before the centre circle. The HUD's other parts (top bar, score, LOVELIVE! letters, song name) are never crossed by notes in any frame, except possibly the song-name plate near the × lane. Its order there was not checked.

### Item 5: hit sounds

- **Port:** silent.
- **Game:** one cue per judgement (section 2), the `_fl` set in the finale.
- **Not verified:**
  - whether a hold's release judgement plays a sound;
  - whether two judgements in the same frame play two cues. CRI cue limits may cap them.

## 4. Root causes

| # | Root cause | Correction |
|---|---|---|
| 1 | `kNoteSize` 0.95 was fitted to one held-note ring in G1. The bracket factor 1.17 was fitted to in-flight frames only. | Measure several game frames with a script, then set the note scale (about 1.04-1.10 × 256) and a bracket factor that gives the game's gap |
| 2 | Wrong asset: `common_circle_05` is a glow | Atlas (3, 1) white and (4, 1) pink, drawn with the tail's path size so that the disc equals the band width |
| 3 | Brackets only on heads; groups count heads only | Event numbering over heads and tails (rule A); draw the tail brackets on the end cap |
| 4 | Draw order | Bands and notes before the centre circle (HUD, gauge fan, mic) |
| 5 | No sound effect path; the output has one voice | A small sound-effect mixer beside the music voice, `sys.acb` cues 25-29 and 32-36, all tracks of a cue mixed |
