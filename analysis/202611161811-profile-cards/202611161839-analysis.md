# P1: eboot trace, first pass (partial; P2 comes next)

Date: 2026-11-16 18:39 (Asia/Jakarta). Step P1 of `plan/202611161811-m12-profile-cards/202611161811-plan.md`. Follows the survey (`202611161811-analysis.md`).

**Result in short:** the eboot names the systems (View Live Show is `scLiveViewer`, the screenshot is "LiveViewSS", profile cards are "Proca") and the save has three empty slots that likely hold them. Most of the code reaches its strings indirectly, so the trace stalled. As the plan allows, **P2 (the shadPS4 run) moves before the rest of P1**: the run fills the empty save slots and shows the screens, and the remaining questions then become data searches.

## Tools this time

- **REA** cannot open this ELF on Windows (its Ghidra provider takes PE only; IDA and Kuna are not configured). The project's own helpers were used instead: the objdump listing `work/eboot.asm` with `work/m11/asm.py`, and Ghidra headless (`dec.ps1`, scratchpad, not committed).
- **Note for later runs:** `dec.ps1` needs its addresses as quoted strings in PowerShell (`-addrs '0x1b994a','0x1be995'`). Unquoted `0x…` numbers are passed as decimals and Ghidra finds no function.

## What the eboot shows

**Scene names** (scene = one screen or mode of the game; `0x5EA6BC` and the debug menu at `0x5FB5F8`): `scLiveViewer` (View Live Show), `scCharacterViewer`, `scStageViewer`, `scCardViewer`, `scUiViewer`, `scSaveLoadTest`. These appear in the debug scene list, so the shipped game has a live viewer scene of its own. Some of these scenes (`scCharacterViewer`, `scStageViewer`, `chr_viewer`, `live_viewer_init.ini`, `./viewer_init/`) are *probably* developer tools.

**View Live Show:**
- Table names `s_liveViewParam`, `s_liveViewCoeffParam`, `s_CameraAppealParam`, `s_CameraLastCutParam` (loaded near `0xF43CB`) and `s_liveViewVoiceParams`.
- `pose_camera_datas.bin` and the voices `eVoice_photoPose*` (Self, SelfPeace, SelfSpot, Pair, PairName1-10). *Hypothesis:* the Camera asks the members to pose for a photo and they answer with a voice line. Message 391, "Take pictures of each member.", fits this.
- UI node names: `liveview_start00`, `liveview_result00`, `photo%02d_00`, `photo_stencil%02d_00`, `photo_eff%02d_00`, `photo_preview_S%02d`, `photo_preview_L00_M`, `photo_image%02d_M`.
- Debug names "LiveViewSS" (*hypothesis:* the screenshot) and "ProcessTestCameraAnim".

**Profile cards ("Proca"):**
- Debug menu: "Preset ProfileCard Select:", "Make ProfileCard with JPEG", "Make Preset ProfileCard", "Save Get Data as ProfileCard", "ProfileCard Download". "TUS Preset ProfileCard: size = %zuKB" (TUS is the PSN title user storage, so downloading cards is online).
- "MyProca" and "OtherProca" (own and received cards), "procaEdit", "edit_photo00/01", and the JPEG title "LP5 Profile Card JPEG by %s".
- Preset table: `ll3::s_preset_profilecard` is loaded in `FUN_00084c70` (`0x84D7C`), which stores the table object in a data manager at `+0x18`. Its readers go through that object, so they have no direct reference; not traced.
- The voice lines `eVoice_profileCard1-10`, `eVoice_profileCardReaded1/2`, `eVoice_profileCardRead<member>Aq` and `eVoice_centerProfileCard` *suggest* the members react when a profile card is read (received).

**Save counters** in the debug save display (`0x20CB31`-`0x20FE4A`): LiveViewPlayCount, ProcaMakeCnt, CameraFocusTime (minutes), MedlayPlayTime, LiveViewPhotoCnt, OtherProcaCnt, PhotoCnt. These match the M7 mission kinds that wait for these screens (`202611071839-analysis.md`).

## The save slots (shadPS4 user folder, from M11 S2)

The game uses four save memories (`sceSaveDataSetSaveDataMemory2`, one folder per slot):

| Folder | Size | Content after M11 S2 |
|---|---|---|
| `sce_sdmemory` | 512 KiB | the main save, 0x59139 bytes used |
| `sce_sdmemory1` | 21 MiB (22,020,096) | all zero |
| `sce_sdmemory2` | 400 KiB (409,600) | all zero |
| `sce_sdmemory3` | 8 MiB (8,388,608) | all zero |

- **Hypothesis**, from the sizes and the load errors 408/410/412 ("Created Profile Cards", "Accepted Profile Cards", "Saved Photos" could not be read):
  - slot 1 holds the 30 photos (about 700 KiB of JPEG each);
  - slot 3 holds 20 profile cards of about 400 KiB (card JPEGs);
  - slot 2 holds 20 records of 20 KiB.
- P2 tests this: after photos and a card are made, the non-zero ranges and the JPEG markers (`FF D8 FF`) show which slot holds what.
