## 1. Executable tools

### `tools/self2elf.py` (SELF → ELF)

- Parses the 0x20-byte SELF header and the 0x20-byte segment entries (`self2elf.py:8-9`, `:25-28`).
- Reads the embedded ELF header and program headers right after the segment table (`:30-33`).
- Builds an output buffer sized to the furthest program header (`:35-36`), clears the section-header fields (`:38`), and copies each **blocked** segment's data to the file offset of the program header whose index sits in bits 20..31 of the flags (`:44-55`).
- Raises an error on encrypted segments (`:47-48`); zlib-decompresses segments flagged compressed (`:51-52`).
- Reports program headers that have no own data and lie inside another one, or have no data at all (zero-filled, for example `SCE_VERSION`) (`:57-63`, `:80-86`).
- **No decryption and no keys.** Works only for fake-signed (plaintext) SELF files.
- Class: **generic PS4.** Already reused (Part 3, `repository/tools/self2elf.py`, unchanged); it converted SIF's eboot and all three PRX files.

### `tools/dynlib.py` (SCE dynamic linking data)

- Finds `PT_DYNAMIC` and `PT_SCE_DYNLIBDATA` (`dynlib.py:64-66`); walks the dynamic tags (`:68-76`); uses `SCE_STRTAB`/`SCE_SYMTAB` inside DYNLIBDATA (`:78`, `:99-104`).
- Decodes needed modules and import/export libraries from `SCE_NEEDED_MODULE`/`SCE_MODULE_INFO` and `SCE_IMPORT_LIB`/`SCE_EXPORT_LIB` tags (`:83-88`).
- Splits symbol names `nid#lib#module` and decodes the library/module IDs with a base-64 alphabet (`:29`, `:38-42`, `:105-109`).
- Reads `SCE_JMPREL` and `SCE_RELA` relocations to find each import's GOT slot and data references (`:111-120`, `:132-140`).
- `name_to_nid` computes a NID: SHA-1 of name + fixed 16-byte suffix, first 8 bytes reversed, base64 with `+-` (`:30-35`).
- Output: text and optional markdown (`:142-175`).
- Class: **generic PS4.** Reused in Part 3 with additions (`--csv`, `--names`, `STUB(...)` parsing).

### Where the NID database comes from

- pt-pc ships **no** NID database. `git ls-files` lists none, and a grep for `nid_db|aerolib|GhidraOrbis|ps4libdoc` finds only `dynlib.py:45`, `:126`, `:130` and `docs/formats/self.md:4`.
- `dynlib.py --nid-db` accepts "GhidraOrbis nid_db.xml or shadPS4 sources" (`:126`). `load_nid_db` parses two formats (`:45-53`):
  - XML attributes `obf="<nid>" sym="<name>"` (GhidraOrbis);
  - `LIB_FUNCTION("<nid>", ..., name)` registrations (shadPS4 HLE sources).
- So the author supplied an external database at run time (Hypothesis: shadPS4, which the README credits, `README.md:173-174`).
- For SIF we now use shadPS4's `src/core/aerolib/aerolib.inl` (`STUB(...)` format) through the parser we added. It names all 559 SIF eboot imports (`analysis/202610311616-sif-executable/202610311655-analysis.md`).

## 2. Package tools

### `tools/pkginfo.py` (PKG inspection, no decryption)

- Reads the PKG header (big-endian), the entry table and entry names (`pkginfo.py:47-106`), the PFS header (little-endian; mode bit names `signed`, `64bit`, `encrypted`, `unknown_0x8`, `:39`, `:109-128`), and the plaintext `param.sfo` (`:131-144`).
- `--extract` writes only **plaintext named entries with id ≥ 0x1000** (the `sce_sys` files) and skips encrypted ones (`:185-195`).
- Its content-flag table names `0x02000000` `GD_AC` and `0x08000000` `UNKNOWN_0x8000000` (`:28-37`). So SIF's and the user's P.T. `content_flags 0x0A000000` (Part 2 follow-up) decode as `GD_AC | 0x08000000`, while pt-pc's retail EU example is `GD_AC` only (`docs/formats/pkg.md:21`). The meaning of `0x08000000` is unknown in pt-pc too.
- Class: **generic PS4.** Our `repository/tools/ps4_meta.py` (Part 2) does the same work and also batches DLC folders. **Reuse:** nothing new to copy. The two flag-name tables are worth adding to `ps4_meta.py` output later.

### `installer/Extractor/Program.cs` (fake-PKG extractor, C#, LibOrbisPkg)

- Uses LibOrbisPkg (LGPL; referenced by source path `$(LibOrbisSource)` in `installer/Extractor/Extractor.csproj:3`).
- Flow:
  1. Check the PKG magic (`Program.cs:43-44`) and read the PKG (`:45`).
  2. **`pkg.GetEkpfs() ?? throw new IOException(RetailMessage)`** (`:48`): LibOrbisPkg derives the PFS key only for fake-signed packages. A null result means a store (retail) package, which is refused with the message at `:9-11`. This is the fake-vs-store test that Part 2 could not run.
  3. Open the outer PFS with that key (`:51-53`), then the inner PFSC-compressed image `pfs_image.dat` (`:54`).
  4. Collect all files outside `sce_sys`/`sce_module` (`:23-28`).
  5. Choose the PSARC (`PSAR` magic) and QAR (footer `aq` at 0x16 of the last 0x24 bytes) (`:29-30`, `:57-59`).
  6. Require `pt14_` in the path list or a known title ID (`:38-39`, `:60-62`).
  7. Copy the three archives into an empty folder and write `source.txt` with content ID, title, region and warnings (`:68-79`).
- Size and truncation checks (`:49-50`, `:71`).
- Class: the PKG/PFS opening is **generic PS4 (fake PKGs only)**; the archive choice and the `LooksLikePt` check are **P.T.-only**.
- **Reuse for SIF:** the pattern (refuse store packages, read the PFS in place, recognise the game by content) is reusable. The code is C# and LGPL-dependent. We have the dump, so a SIF port needs no PKG extraction at first. If a PKG installer is wanted later, this is the model.

### `tools/patch_liborbis_readers.py`

- Applies two read fixes to the LGPL LibOrbisPkg source (short reads in `PFSCReader.cs` and `MemoryMapped.cs`) (`patch_liborbis_readers.py:9-15`). It refuses unexpected source versions (`:22-23`).
- Class: **generic** (LibOrbisPkg maintenance). Reuse only together with LibOrbisPkg.

## 3. Container tools

### `tools/psarc.py` (PlayStation PSARC)

- Big-endian header `PSAR`, version, compression, TOC length, entry size/count, block size, flags (`psarc.py:6`, `:9-13`).
- TOC entries: MD5 of the path, first block, 40-bit size and offset (`:16-23`); then a block-size table whose width depends on the block size (`:24-28`).
- Blocks are zlib unless stored at full size (`:34-50`). Entry 0 is the manifest of names (`:61-62`). Format doc: `docs/formats/psarc.md:7-25`.
- Class: **generic PS4/Sony** (PSARC is a Sony archive format used by many games). **Not used by SIF** (no `PSAR` files, Part 2 section 3).

### `tools/qar.py` (Fox QAR texture archive)

- Footer at the end with magic `0x7161` (`qar.py:6-7`, `:20-24`); 16-byte entries `PathCode64, offset >> 4, size` (`:10`, `:27-30`); optional name strings (`:31-37`).
- Names come from `pathid_list_ps4.bin` through `pathcode.py` (`:4`, `:59-60`). Texture extensions are Fox-specific (`:11`).
- Class: **Fox Engine-only.** Not usable for SIF.

### `tools/fpk.py` (Fox package)

- Optional whole-file Fox encryption (`foxcrypt`) (`fpk.py:6`, `:28-30`); header magic `foxfpk` (`:8`, `:31-33`); entries with offset, size, name and MD5 of the name (`:34-41`); references (`:42-45`).
- Per-entry XOR decryption keyed by the Fox `StrCode64` hash of the file name (`:13-21`).
- Class: **Fox Engine-only.** Not usable for SIF.

## 4. Shader tools (from the subagent report; key lines re-checked by me)

### `tools/gcn.py` (GCN disassembler and pseudo-code lifter)

- **Input:** raw GCN code bytes. It does not parse the `OrbShdr` footer. `--offset`/`--length` cut code out of a larger file, and decoding stops at `S_ENDPGM` (`gcn.py:498`; CLI `:1145-1156`, help text "Disassemble raw GCN (GFX7, PS4) shader code" at `:1145`, checked).
- **Encodings:** decoded by mask and value (`:19-36`): SOP1, SOP2, SOPC, SOPK, SOPP, SMRD, VOP1, VOP2, VOP3, VOPC, VINTRP, DS, MUBUF, MTBUF, MIMG, EXP. FLAT is not decoded. GFX7, the PS4's GCN generation, has no SDWA/DPP/VOP3P.
- **Opcode names** come from **shadPS4's `src/shader_recompiler/frontend/opcodes.h`**, parsed by regex at run time (`load_opcodes`, `:56-76`). The default path is `<pt-pc>/../shadPS4/...` (`:10`, checked), so the author kept a shadPS4 checkout next to pt-pc. A missing file raises an error (`:62`, checked).
- **Limits:**
  - Unknown words become `.word` (`:238`), and encodings without a decoder become `<enc>_UNHANDLED` (`:451`).
  - The VOP3 source count and register widths are guessed from opcode names (`:202-231`, `:455-466`).
  - The `Lifter` (`:685-1124`) does not lift DS ops (`:783`).
- **Dependencies:** standard library only, plus the `opcodes.h` file.

### `tools/gcnexpr.py` (expression lifter)

- Turns the instruction list into expression trees per register (`:16-46`), with constant folding and simplifications (`:74-121`, `:506-507`).
- **Control flow:**
  - forward branches and exec-mask `saveexec` patterns become if/else regions (`:253-312`, `:340-346`, `:408-437`);
  - conditional writes become selects (`:154-187`);
  - discards are recognised (`:347-354`, `:487-489`).
- **Any backward branch (loop) raises `LoopError`** (`:237-239`, checked). `fsop.py` then prints "expression form unavailable" (`fsop.py:442-445`, checked). This is the "22 looping stages" with no expression output (`docs/formats/fsop.md:115-116`).
- **Output:** GLSL-like lines (`sample(...)`, buffer loads, temporaries, exports, `discard`) (`:651-722`). It is not compilable GLSL:
  - values are only `float` or `bool` (`:716`);
  - buffer stores are dropped (`:604-605`);
  - unknown ops become calls (`:515`).
- **Needs** an `env` dict for resource and constant names (`gcn.py:729-731`, `gcnexpr.py:595-602`).

### `tools/fsop.py` (Fox shader pack)

- **`.fsop` packs:** name-length-prefixed entries whose stage blobs are XORed with 0x9C, recognised by a Fox stage magic (`read_pack`, `:213-232`; `:18`).
- **Each stage:** a 0x24-byte Fox header (`:20`, `:97-101`), then the **standard Gnm shader file header (`Shdr`)**, usage slots, and VS/PS semantics (`parse_stage`, `:103-149`; only VS and PS). The doc says this is the same layout `.sb` files use (`docs/formats/fsop.md:58-59`).
- **Code length** comes from the footer: `blob.find(b"OrbShdr", code_offset)`, then `info_bits >> 8` (`:151-153`, checked).
- **PSSL reflection** (resource, constant and semantic names) follows the Gnm part (`parse_reflection`, `:173-210`). `build_env` joins it with the usage slots to name registers (`:265-360`).
- **Commands:** `list`, `info --mode pseudo|asm|json|expr`, `extract` (parallel) (`:461-561`).
- **Class:** the Gnm/`Shdr`/usage-slot parsing is **generic PS4**, but it is hard-wired to the Fox wrapper (`base = FOX_HEADER.size`, the Fox magic check, `gnm_end` from the Fox header; `:97-102`, `:161`). The pack format and the XOR are **Fox-only**.

### How the port's shaders were made

`docs/formats/fsop.md:6-8`: "The port's GLSL shaders were written from these" listings. Nothing in the tools generates GLSL (subagent, Inference). So pt-pc **hand-wrote its ~120 GLSL shaders** from the disassembly and expression listings of P.T.'s 4 packs.

### Test on SIF data (this part)

I copied `tools/gcn.py` to `repository/tools/gcn.py` with the MIT notice. It reads shadPS4's `opcodes.h` at run time; nothing GPL is copied. For each test shader I took the `info_bits >> 8` bytes **directly before** its `OrbShdr` footer (`BINARY_INFO` layout `<7sBIBBBBQI`, `fsop.py:25`).

- **Three shaders embedded in the SIF eboot** (`work/elf/eboot.elf` at 0x6437C0, 0x643DE8, 0x644440; 436, 468 and 436 bytes): each disassembles to 73-79 lines with **0 unknown words**, ending `exp param0 ...` / `s_endpgm` (vertex shaders). The listings are only in `work/shader*.asm`.
- **300 randomly chosen shaders** (seed 1) out of the 26,196 `OrbShdr` footers in `CUSA24620/shader/ps4/sh_custom.pac`: **300/300 decode cleanly**. None has `.word` or `UNHANDLED`, and all reach `s_endpgm`. All are footer version 7. The low 6 type bits are 1 (287 shaders) and 5 (13); I haven't decoded what those values mean.

So SIF's shaders are standard Gnm shader binaries with the code directly before the footer, and pt-pc's disassembler handles them unchanged. This does not prove the lifter works on all of them, or that loops are rare.

## 5. `tools/audio_dump.py` and how game behaviour was recovered from the eboot

### What it does (subagent report; key lines re-checked)

- **Pipeline** in `main()` (`audio_dump.py:908-953`):
  1. unpack Fox `.sbp` sound packages;
  2. parse the Wwise banks and write JSON;
  3. extract `.wem` files, decode them with `vgmstream-cli` and measure levels;
  4. link subtitles;
  5. resolve names and find references;
  6. build an event index.
- **Inputs:** a dump tree including `dump/elf/eboot.elf` (made by `self2elf.py`) and `dump/strings/eboot_strings.txt` (`:34-49`, `:42-43`, checked).
- **Most behaviour comes from the Wwise banks**, not from the eboot (`Graph`, `:615-827`).
- **The eboot is used in two small ways:**
  1. **Name candidates.** Its strings join a pool of candidate names, which are hashed (FNV-1 32) and matched against bank IDs (`:297-337`, `:320-324`, `:416-529`). No tool in `tools/` creates `eboot_strings.txt` (subagent).
  2. **Immediate scan:**
     - For each known 32-bit ID, `data.find` searches the first executable `PT_LOAD` segment (`executable_segment`, `:539-545`, checked).
     - Each hit is checked with **capstone** in x86-64 mode, starting at 8 points 96-103 bytes before the hit. The hit counts if at least 3 of the 8 runs agree on the instruction that holds the immediate (`:551-566`, checked).
     - `capstone` is imported only if the ELF exists (`:570-572`, checked). Results go to `references.json` (`:588-602`).
- **No** hard-coded eboot addresses, no emulation, and no use of the import table or call graph (subagent).
- `docs/formats/audio.md:175-194`:
  - names are mined from Lua, packages, fox2, executable strings and wem markers;
  - event sources include "immediates in the executable (62 sites)";
  - 186 of 247 events are named.
- **Class:**
  - Generic PS4 ELF: the immediate-scan helpers (`executable_segment`, `instruction_with_immediate`, `eboot_references`) and the string-candidate approach (`identifier_runs`, `expand_candidate`).
  - Fox/P.T.-only: everything Wwise or Fox (`wwise_bank` v88, `sbp`, `fsm`, `foxhash`, FNV names).

### How behaviour was recovered, overall

1. **Executable:** `self2elf.py` produces a plain ELF, and `dynlib.py` with an external NID list (Hypothesis: shadPS4) names the imports (section 1).
2. **Strings and immediates** from the eboot, hashed against data IDs (`audio_dump.py`; `docs/formats/geom.md:69`, per Part 1).
3. **Shaders:** `fsop.py` + `gcn.py` + `gcnexpr.py` listings, then hand-written GLSL (section 4).
4. **Game logic:** the docs say facts were "read from the game's code" (`docs/formats/fsm.md:9`, `docs/formats/vfx.md:10`, `docs/formats/motion.md:190`, per Part 1). No tool in `tools/` decompiles game logic, and the repository has no disassembler project. Hypothesis: an interactive disassembler (Ghidra/IDA) was used by hand.
5. **Run-time comparison:** shadPS4 was "my reference for how the original behaves" and for checking frames (`README.md:173-174`).
6. **Big help unique to P.T.:**
   - Much of the logic was in the game's own Lua, decrypted with `foxcrypt.py` (`docs/formats/foxcrypt.md:4-6`).
   - The MGSV modding community has documented the Fox Engine formats (GzsTool, `docs/formats/textures.md:35`).
   - SIF has neither: no script VM and an in-house engine (Part 3).
