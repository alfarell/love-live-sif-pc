# M6: screen transitions (fades)

Created: 202611021452 (Asia/Jakarta). Follows `202611021435-analysis.md`.

## 1. What the data offers

- Each ui2 screen package has "in" clips (`a001`) and a few "out" clips (`a002`): title 1, top menu 1, song select 4, result 2. Most parts of a screen have no "out" clip, so on their own the "out" clips would leave most of the screen standing.
- Material colour tracks (`ANMT` type 6) are RGB only. The game's clips fade parts to and from **black** through the colour, not through alpha.
- `00_common` has loading layouts `uil0002_LoadingLayout00`, `uil0003_LoadingLayout01` and `uil0004_LoadingSkipLayout00`. The game probably shows them between screens (*Hypothesis*; not traced and not used yet).

## 2. Port (`src/app/fade.h`, `ScreenFade`)

- A screen fades in from black over 0.3 s when it opens.
- When it is left (confirm or back), it plays `a002` on every instance that has it, ignores further input and fades to black over 0.3 s. Only then does the screen function return.
- The fade is one black layer drawn over the finished frame (a disc whose radius is the window diagonal, via `Renderer::DrawCircle`). Per-part alpha was tried first: overlapping parts showed through each other mid-fade.
- Used by the top menu, song select and result screen (in and out), and the title (out; its stages already fade themselves).
- Between screens, the blocking load shows the cleared, near-black window. So a screen change is: fade out → dark while loading → fade in.
- The 0.3 s length and the overall sequence are guesses (marked as a `shortcut:` in `fade.h`).

## 3. Check

- With the fade slowed to 3 s for the captures (restored to 0.3 s afterwards):
  - `work/m6/fade_c.png`: the top menu about 1 s into its fade-out, evenly dimmed;
  - `work/m6/fade_d.png`: the song select fading in.
- In the slowed run, the top menu's short "out" clip finishes long before the screen fade, so its parts sit black on a still-visible screen. At 0.3 s the two run together.
