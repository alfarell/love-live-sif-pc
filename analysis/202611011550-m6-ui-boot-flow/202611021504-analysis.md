# M6: loading screen between screens

Created: 202611021504 (Asia/Jakarta). Follows `202611021500-analysis.md`.

## 1. The layouts

`ui2/00_common` has `uil0002_LoadingLayout00` and `uil0003_LoadingLayout01`. Viewed with `--ui 00_common:<layout>:a003` (captures `work/m6/load_uil0002_LoadingLayout00.png`, `load_uil0003_LoadingLayout01.png`), both look the same: the word "Loading" in the bottom-right corner on a dark screen. In the boot flow it shows as "Loading..."; the dots appear to animate. What separates the two layouts, and `uil0004_LoadingSkipLayout00`, is not known.

## 2. Port

- `LoadingScreen` (`src/app/fade.h`) loads `ui2/00_common` once when the boot flow starts, with its text so the label renders. `Show()` presents `uil0002_LoadingLayout00` twice, so it stays on screen while the caller blocks.
- `main.cpp` shows it before each blocking load: top menu, song select, live, and the result after a finished song.
- A screen change now goes: fade out → "Loading..." during the load → fade in.
- **Cost:** loading `00_common` once takes 1.2 s in Release (0.54 → 1.75 s after start, `--select`), and about 1.2 s in Debug.

## 3. Check

- `work/m6/loading_a.png`, captured while song 0030 loads after the song select: "Loading..." in the corner.
- Debug and Release are rebuilt, and all 6 tests pass.

## 4. Open

- The loading frame is static during the load. Loads are blocking, so the dots cannot animate; that would need loading on a thread.
- Which loading layout the game uses where, and its real screen-change sequence and timing.
- The 1.2 s start-up cost could drop by loading only the loading layout's parts instead of the whole `00_common` package.
