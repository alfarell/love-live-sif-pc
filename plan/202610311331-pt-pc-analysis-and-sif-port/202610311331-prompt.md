# Prompts for Claude Code: pt-pc analysis and SIF port

Run these in Claude Code with the working directory set to the main project folder:
`E:\Projects\Software Reverse Engineering\Love Live SIF (PS4)`

If Claude Code does not already have the other two folders, start it with them added, for example `claude --add-dir "D:\Games\PS4\pt-pc" --add-dir "D:\Games\PS4\Love Live School Idol Festival"`.

The work is split into parts (see `202610311331-plan.md` in this folder). Use the **Master prompt** for every session; it picks up the next unchecked part by itself. Use a **Part prompt** when you want a specific part, or the **Resume prompt** if a session was cut off.

---

## Master prompt (use for every session)

```
You are continuing a long reverse-engineering project: a PC port of the PS4 game "Love Live! School Idol Festival" (CUSA24620), modeled on pt-pc, an existing project that runs the PS4 game "PT" on PC from a PS4 dump. First we analyze pt-pc, then analyze our game, then design the port.

Folders:
- Main project (read/write): E:\Projects\Software Reverse Engineering\Love Live SIF (PS4)  [current directory]
- pt-pc reference repository (READ-ONLY): D:\Games\PS4\pt-pc
- SIF game assets and dump (READ-ONLY): D:\Games\PS4\Love Live School Idol Festival

Start by reading, in the main folder: README.md, CLAUDE.md, INSTRUCTIONS.md, and plan\202610311331-pt-pc-analysis-and-sif-port\202610311331-plan.md. Also read any analysis\ and plan\ files created since, newest first, so you know what has already been found.

Task: find the first part in the plan that has unticked boxes and whose dependencies are done, and complete that part fully. Do only that part in this session.

How to work:
1. Get the real current time with `date` (Asia/Jakarta) for timestamps. Do not guess it.
2. Create the part's analysis topic folder: analysis\<YYYYMMDDHHmm>-<topic>\ . Write results to <YYYYMMDDHHmm>-analysis.md inside it (new timestamped file for each further write-up on the same topic; never overwrite earlier ones). Part 11 writes to plan\ with <YYYYMMDDHHmm>-plan.md instead.
3. Read the actual files. Do not rely on general knowledge of PS4 or emulator internals instead of reading the source; use that knowledge only to know where to look.
4. For every finding, cite the file path and line number or function name. Label anything unverified as "Hypothesis". Keep a separate "Open questions" section.
5. Work in small steps and save notes into the analysis file as you go (do not keep everything for the end), so a cut-off session loses nothing.
6. For big surveys (many files or directories), use subagents to read different areas in parallel and ask each for a short, cited summary. Do the synthesis yourself.
7. When a repeatable task is better done by a script (counting, listing, extracting imports or NIDs, hashing), write the script into repository\tools\ with a short README comment, run it, and save the output under repository\tools\data\ . Pass paths as arguments; do not run scripts from inside the read-only folders.
8. Tick the boxes in the plan file as each item is completed (edit the checkbox in place), and fill in the part's "Output folder" line with the real folder name. If you discover that the plan is missing something, do not rewrite it: add a short "Plan changes needed" section to your analysis file and mention it in your final summary.
9. At the end, verify: re-open the analysis file, check that each claim has a citation, that all checked boxes have real output, and that no file outside the main folder was changed.

Hard rules:
- Never modify, move, delete, or create files inside pt-pc or the SIF assets folder. That includes build output, caches, and git operations that write (read-only git commands such as log, show, and ls-files are fine). Build or test things only in a subfolder of the main project named work\ if it is truly needed, and ask first.
- Do not copy large binaries (the 11 GB PKG, eboot.bin, assets) into the main folder. Analyze them in place. Do not put any game asset, eboot, or key into any file we write; short hex dumps and string excerpts for analysis are fine.
- Do not install system-wide tools without asking. Prefer Python packages in a virtual environment under work\ .
- If something is blocked (missing tool, encrypted data, no access), write down exactly what is blocked and what is needed, finish the rest of the part, and stop there rather than guessing.
- Ask me before doing anything large or irreversible.

When you finish the part, reply with: (1) what part you completed, (2) the 5 most important findings, (3) the analysis folder and files you created, (4) open questions or blockers, (5) which part is next. Keep it short. Then stop; do not start the next part.

Language: reply in the language I write in. Write all project files in English.
```

## Part prompts (optional; use to run one specific part)

Each one is used together with the master prompt rules. Paste the master prompt first and replace the "find the first part" sentence with the line below, or send the part prompt as a follow-up in the same session.

### Part 0: Setup and orientation

```
Do Part 0 of the plan. Confirm access to all three folders, inventory the tools on this machine (python and its packages such as pyelftools, lief, capstone; git; cmake; compilers; any disassembler), record the pt-pc commit hash and date with read-only git commands, and write the setup note. Do not install anything; list what is missing and what I should install.
```

### Part 1: pt-pc survey

```
Do Part 1 of the plan. Survey pt-pc: README and docs fully, license and what it allows, directory map to depth 3 with a purpose for each folder, lines of code per language and folder, build system, third-party dependencies, entry point and startup flow. Produce a first architecture sketch and a list of questions for the next parts.
```

### Part 2: pt-pc loader and memory model

```
Do Part 2 of the plan. Find out exactly how pt-pc loads the PS4 eboot.bin and any modules, handles SELF/ELF, decryption, relocations, TLS, NID resolution, how it emulates the PS4 memory layout on PC, and how execution of guest code starts. Trace the real code path from the entry point to the first guest instruction, with file and function citations. List every place that depends on the specific game.
```

### Part 3: pt-pc system layer

```
Do Part 3 of the plan. Document how pt-pc implements and registers PS4 library functions (libkernel, libc, libSce* and others), the threading and sync primitives, memory calls, file calls, and its stub strategy. Write a script that extracts every implemented function and NID into a CSV or JSON in repository\tools\data\, and summarize implemented, stubbed, and missing per library.
```

### Part 4: pt-pc graphics and shaders

```
Do Part 4 of the plan. Document how pt-pc receives PS4 GPU commands and turns them into host graphics calls: API and window library, command buffer handling, draw and state translation, render targets, flips and display, shader origin and translation, shader cache, and fences. State what the design assumes about the game, and what would break for a different game.
```

### Part 5: pt-pc other subsystems

```
Do Part 5 of the plan. Document audio, input, filesystem and path mapping (app0, savedata, and others), save data and system services, video playback, configuration and any debug UI in pt-pc. For each, say what is implemented, how, and what a different game would likely need.
```

### Part 6: game-specific vs generic

```
Do Part 6 of the plan. Find everything in pt-pc that is specific to the PT game (addresses, patches, hooks, title ID, file names, workarounds) and classify each major component as generic, configurable, or game-specific. Review tools, tests, examples, installer, and assets. Write the checklist for supporting a new game in this architecture.
```

### Part 7: pt-pc synthesis

```
Do Part 7 of the plan. Read all notes from Parts 1 to 6 and write one consolidated pt-pc architecture document with diagrams (Mermaid is fine), a subsystem matrix, a glossary, and remaining risks. Check the earlier notes for contradictions and correct them, noting each correction.
```

### Part 8: SIF inventory

```
Do Part 8 of the plan. Inventory the SIF folder in place: directory tree with sizes for CUSA24620, DLC, Extracted, savedata; PKG metadata read without extracting it; eboot.bin, modules, sce_sys; census of file types; identification of unknown formats by magic bytes; duplicates between the dump, PKG, and DLC. Do not copy the PKG or any large file.
```

### Part 9: SIF executable analysis

```
Do Part 9 of the plan. Analyze SIF's eboot.bin and modules: SELF or ELF, decrypted or not, segments, entry point, required libraries, the full import list with NIDs into repository\tools\data\, strings, and engine and middleware identification. Find the graphics, audio, online, and asset loading behavior and any integrity checks. Say clearly what is verified and what is hypothesis.
```

### Part 10: Gap analysis

```
Do Part 10 of the plan. Compare the SIF import list against the pt-pc implemented list (covered, stubbed, missing), then per subsystem mark reusable, needs adaptation, needs new work, or unknown, with effort and risk. List the first things that would stop SIF from booting and the blocking unknowns with a way to resolve each.
```

### Part 11: Port design and roadmap

```
Do Part 11 of the plan. Using all earlier notes, decide the base approach (fork or adapt pt-pc, reimplement with pt-pc as reference, or hybrid), considering the license. Design the SIF port architecture and the layout under repository\ , define ordered milestones with testable exit criteria, the tooling to build first, a risk register, and write a new plan file (with checklist) and a new driver prompt for the implementation phase in plan\.
```

## Tips for running this

- Run one part per session, then start a fresh session for the next one. The plan file and the analysis folders carry the state, so nothing is lost.
- Parts 3, 4, and 5 do not depend on each other, and Part 8 can run alongside Parts 1 to 7, so they can be run in parallel in separate sessions. If you do that, give each session a different part prompt so they do not pick the same part.
- Check the final summary and open questions at the end of each part before starting the next one.
