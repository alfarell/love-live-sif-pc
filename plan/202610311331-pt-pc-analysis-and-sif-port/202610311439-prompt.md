## Master prompt

```
You are continuing a long reverse-engineering project: a PC port of the PS4 game "Love Live! School Idol Festival" (CUSA24620). The reference is pt-pc, a native PC port of the PS4 game "P.T.". Part 1 found that pt-pc is NOT an emulator: it rewrote the game logic in C++ and reads only the game's data files; the PS4 eboot was studied offline. So we analyze SIF early, study pt-pc's method and reusable parts, choose the port approach (rewrite, emulation, or hybrid), then design the port.

Folders:
- Main project (read/write): E:\Projects\Software Reverse Engineering\Love Live SIF (PS4)  [current directory]
- pt-pc reference repository (READ-ONLY): D:\Games\PS4\pt-pc
- P.T. game copy, the input pt-pc reads (READ-ONLY): D:\Games\PS4\pt-pc-game
- shadPS4 emulator source, GPL-2.0, reference and NID names (READ-ONLY): D:\Games\PS4\shadPS4
- SIF game assets and dump (READ-ONLY): D:\Games\PS4\Love Live School Idol Festival

Start by reading, in the main folder: README.md, CLAUDE.md, INSTRUCTIONS.md, and plan\202610311331-pt-pc-analysis-and-sif-port\202610311439-plan.md (the current plan; the older 202610311331-plan.md is superseded). Also read the analysis\ and plan\ files created since, newest first.

Task: find the first part in the plan that has unticked boxes and whose dependencies are done, and complete that part fully. Do only that part in this session.

How to work:
1. Get the real current time with PowerShell `Get-Date -Format yyyyMMddHHmm` (Asia/Jakarta). Git Bash `date` shows the wrong zone.
2. Create the part's topic folder with that timestamp: analysis\<YYYYMMDDHHmm>-<topic>\<YYYYMMDDHHmm>-analysis.md. Parts 8 and 10 write to plan\ with <YYYYMMDDHHmm>-plan.md instead. Never overwrite earlier files; further write-ups get a new timestamped file.
3. Read the actual files. Use general knowledge of PS4 or engines only to know where to look.
4. Cite the file path and line number or function name for every finding. Label anything unverified as "Hypothesis". Keep an "Open questions" section.
5. Save notes into the analysis file as you go, so a cut-off session loses nothing.
6. For big surveys, use subagents to read different areas in parallel and ask each for a short, cited summary. Spot-check their key claims and do the synthesis yourself.
7. Repeatable tasks (listing, counting, parsing headers, extracting imports or NIDs, hashing) go in a script in repository\tools\ with a short header comment; run it with `py -3.14 -I`, pass paths as arguments, save output under repository\tools\data\. Never run scripts from inside the read-only folders; to use a pt-pc tool, write our own version or copy it into repository\tools\ with its MIT notice and source path.
8. Tick the plan boxes in place as items are completed and fill in the part's "Output folder". If the plan is missing something, add a "Plan changes needed" section to your analysis file and mention it in your summary; do not rewrite the plan.
9. At the end, verify: re-open the analysis file, check citations, check that every ticked box has real output, and check that nothing outside the main folder changed (in pt-pc use `git --no-optional-locks status --short`).

Hard rules:
- Never modify, move, delete, or create files inside pt-pc, the SIF assets folder, the P.T. game folder, or shadPS4, including build output, caches, and writing git operations. In pt-pc use only `git --no-optional-locks ...`, `log`, `show`, `ls-files`.
- Do not copy large binaries (the PKG, eboot.bin, assets) into the main folder. Converted binaries (for example an ELF made from the eboot) go only in work\, which is not committed. Never put game assets, eboot bytes, or key material (keystone, license files) into files we write; short hex dumps and string excerpts are fine.
- Do not install anything system-wide without asking. Python packages only in a venv under work\, after I approve. Use the REA MCP tools for disassembly; ask before downloading Ghidra or other tools.
- If something is blocked (missing tool, encrypted data, no access), write down exactly what is blocked and what is needed, finish the rest of the part, and stop there rather than guessing.
- Ask me before doing anything large or irreversible.

When you finish the part, reply with: (1) what part you completed, (2) the 5 most important findings, (3) the folder and files you created, (4) open questions or blockers, (5) which part is next. Keep it short. Then stop; do not start the next part.

Language: reply in the language I write in. Write all project files in English.
```

## Part prompts

Send one together with the master prompt (in place of its "find the first part" sentence).

### Part 2: SIF inventory
```
Do Part 2 of the plan. Inventory the SIF folder in place: tree with sizes for CUSA24620, DLC, Extracted, savedata; PKG header and entry list read without extracting (fake PKG or store PKG?); param.sfo fields; eboot, modules, sce_sys; file type census; unknown formats by magic bytes; the 1 MiB vs larger DLC PKGs; duplicates between dump, PKG, and DLC; engine hints from the file tree.
```

### Part 3: SIF executable and engine identification
```
Do Part 3 of the plan. Analyze SIF's eboot.bin and sce_module PRX files: SELF or ELF, encrypted or plaintext, segments, entry point, imports with NIDs into repository\tools\data\ with the script. ```
```

### Part 4: pt-pc offline RE toolchain
```
Do Part 4 of the plan. Read pt-pc's offline reverse-engineering tools (self2elf, dynlib, pkginfo, the installer extractor, gcn, gcnexpr, fsop, audio_dump, psarc, qar, fpk) and their docs. Explain how each works, where the NID database comes from, how game behaviour was recovered from the eboot, and classify each tool as generic PS4, Fox Engine-only, or P.T.-only, with what we should reuse for SIF.
```

### Part 5: pt-pc data access and engine services
```
Do Part 5 of the plan. Document pt-pc's data access (Vfs and archive readers), its format readers, its engine services (logging, crash reports, threading, settings, user data, saves, update check, OS layer), the Lua script layer, and how src/game is organized and driven from RunGame. Mark what is generic, Fox Engine-specific, and P.T.-specific, and what SIF would need in any approach.
```

### Part 6: pt-pc renderer, audio, input
```
Do Part 6 of the plan. Document pt-pc's renderer architecture (Renderer, SceneRenderer, pt::gpu::Device, Vulkan and D3D12 backends, frame flow), its shaders and build path, textures, audio (Wwise data without the Wwise runtime, mixing, output), input mapping, and video if any. Resolve whether D3D12 is used by the game. Note what SIF, a rhythm game, could reuse and its timing needs.
```

### Part 7: pt-pc specific vs generic, testing, synthesis
```
Do Part 7 of the plan. Find all P.T.-specific code, build the subsystem matrix (generic, configurable, Fox Engine-specific, P.T.-specific), review tests, walkthrough testing, examples, installer, assets, document how the user supplies the game, write the consolidated architecture document and glossary, the checklist for a pt-pc-style port of another game, and list corrections to earlier notes.
```

### Part 8: Port approach decision
```
Do Part 8 of the plan. Using Parts 3 and 7, compare A (rewrite like pt-pc), B (emulation/HLE like shadPS4), and C (hybrid) for SIF with effort, risk, legal fit, reusable pt-pc code, and needed references. ```
```
```
Do Part 9 of the plan for the approach chosen in Part 8: list what must be built (formats and game systems for a rewrite, or imports vs the HLE reference for emulation) as CSV plus summary, rate each subsystem, estimate effort and risk, list blocking unknowns with how to resolve them, and list the first things that would stop SIF from booting.
```

### Part 10: Port design and roadmap
```
Do Part 10 of the plan. Design the SIF port architecture and the repository layout, define ordered milestones with testable exit criteria, list the first tools to build, write the risk register, and produce a new plan file with its own checklist and driver prompt for the implementation phase, in plan\.
```
