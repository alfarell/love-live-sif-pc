## 2. The options compared

### Evidence base

- **SIF executable (Part 3):**
  - Fake-signed plaintext eboot, position-independent, SDK 5.05.
  - In-house native C++ engine ("lp5") from the arcade game; **no script VM**; about 19,800 functions including middleware (P.T.: about 68,400, but much of P.T.'s logic was Lua).
  - Middleware is statically linked: CRI ADX2 (HCA audio, not encrypted in the sampled files), CRI Sofdec2 (202 USM videos), CRI FS, Bullet, zlib, libjpeg.
  - Graphics: 87 low-level GNM imports; about 27,000 precompiled GCN shader binaries (`OrbShdr` v7).
  - Only 559 system imports, all named (Part 3 follow-up).
- **SIF data (Part 2):**
  - About 3,550 `ARC\0`/`cmp\0` `.pac` archives (90% of the 21.8 GiB) with plain-text entry names, plus CRI `.awb`/`.usm`.
  - The DLC data is already in the dump; the DLC packages are entitlements.
- **pt-pc (Part 7, synthesis):** its reusable core is the platform layer, the graphics API layer (Vulkan/D3D12), logging/crash/threads, installer/update, and the headless test method. Everything Fox Engine or P.T.-specific is not reusable. Its port checklist marks game logic, shaders, CRI audio and video as SIF's largest gaps (Part 7 §7).
- **shadPS4 coverage of SIF** (new in this part):
  - Script `repository/tools/nid_coverage.py` → `repository/tools/data/sif-shadps4-coverage.csv`. shadPS4 registers 5,052 NIDs (`LIB_FUNCTION`).
  - **Every SIF eboot import is registered** except `libc` (29/91) and `libSceNpToolkit2` (0/181). Examples: GNM 87/87, VideoOut 13/13, Pad 6/6, SaveData 12/12, AppContent 6/6, AudioOut 6/6, kernel 66/67.
  - The gaps are the libraries SIF ships itself. shadPS4 loads `libc`, `libSceFios2` and `libSceNpToolkit2` from the game's `/app0/sce_module/` as guest code: module table flags `IsGame` (`D:\Games\PS4\shadPS4\src\core\libraries\sysmodule\sysmodule_table.h:31`, `:370-371`, `:624`), loaded by `sysmodule_internal.cpp:137-141`.
  - "Registered" may still mean "stub", so this is an upper bound. **SIF has not been run in shadPS4.**

### Comparison

| Criterion | A: rewrite (pt-pc style) | B: own HLE runtime (MIT) | C: hybrid on shadPS4 (GPL) |
|---|---|---|---|
| **What runs** | New C++ game; original data only | SIF's eboot on our own loader + HLE + GNM/GCN translator | SIF's eboot on shadPS4's loader + HLE + recompiler, with our PC layer |
| **Main work** | Recover all game logic from ~20k unnamed native functions (no scripts); write CRI ADX2 runtime (HCA, ACB cues) and USM video decoding; write `.pac` readers and all asset formats; write a renderer and re-author the shaders needed (from ~27k GCN binaries, vs P.T.'s ~120 hand-written) | Write the ELF loader/linker, kernel/libc HLE, ~25 service libraries, a PM4 command-stream translator and a GCN → SPIR-V recompiler | Get SIF to boot and render on shadPS4, fix SIF-specific gaps (stubs, NpToolkit offline behaviour, GPU features), add the rhythm-timing and PC layer |
| **Effort** | Very large (multi-year for one person, Hypothesis). pt-pc needed ~140k lines for a short teaser with Lua and documented formats | Very large (an emulator from scratch) | Medium; unknown until first boot |
| **Risk** | High: complete-logic recovery without symbols; scoring/judgement and menu/UI fidelity; shader count | High: GPU emulation correctness | Medium: unknown shadPS4 compatibility with SIF; upstream changes; GPL |
| **Fidelity** | Only what is reimplemented | Original code | Original code |
| **Rhythm timing** | Full control (audio-clock notes, per-event input timestamps) | Must make `sceAudioOut`, clocks and `scePadRead` low-latency | Same as B, inside shadPS4 |
| **Legal fit** | Good: user's own dump, no Sony decryption, MIT code; entitlements from the user's own DLC | Same | Same for data. **Port becomes GPL-2.0** (shadPS4 license); pt-pc's MIT code may be included in a GPL work |
| **Reusable pt-pc code** | Platform layer, RHI (Vulkan/D3D12), Renderer shell, shader toolchain, logging/crash/threads, settings/user data, installer/update, test method; offline tools `self2elf`, `dynlib`, `gcn`, `gcnexpr` | Offline tools; `vk_context`, present path, pipeline-cache store, audio output layer, input raw layer (Part 6 §7) | Same as B, plus the walkthrough test method and installer |
| **References needed** | Disassembler (REA tools available; Ghidra on request); shadPS4 as **behaviour reference only** (run SIF there to compare, as pt-pc did, `pt-pc/README.md:173-174`); CRI format knowledge (public tools such as vgmstream for HCA, Hypothesis) | shadPS4 as read-only reference | shadPS4 (provided) |

### Why A is still a valid primary plan

- It keeps the port **MIT-compatible** and independent of upstream emulator code.
- It gives **full control over timing**, the main quality bar for a rhythm game (Part 6 §7).
- It follows the proven pt-pc model the project set out to copy (`INSTRUCTIONS.md` §1, §4 Phase 4: "Prefer adapting pt-pc's design").
- The first phase (understanding all data formats) is useful for C too (debugging, mods, tools), so early work is not lost if the plan switches.

## 3. Consequences for the project

1. **License hygiene during A:** **do not copy any shadPS4 code** into `repository/`. Reading it, and running it as a separate program for behaviour comparison, is fine. Copying would force the port to GPL. pt-pc code may be copied with its MIT notice (already done for `self2elf.py`, `dynlib.py`, `gcn.py`). Tools that read shadPS4 files at run time (`dynlib.py --nid-db`, `gcn.py --opcodes`) copy nothing and are fine.
2. **Keep C cheap:** build A's layers so they could sit on top of an emulated game too:
   - data tools and format readers;
   - the timing/audio-clock layer;
   - input with per-event timestamps;
   - settings, user data, the installer;
   - the headless test runner.
3. **Rhythm requirements apply to both plans** (Part 6 §7):
   - notes follow the *played* audio clock (output latency compensated, user calibration);
   - per-event input timestamps;
   - a small audio buffer;
   - low-latency present modes.
4. **Online:** offline only. Rankings, TUS and matching are not reimplemented against any server. DLC = the user's own installed packages.
5. **Parts 9 and 10** follow plan A (Part 9 "If A" items). The C items are kept as notes for the fallback (section 6).

## 4. Checkpoints for plan A

The user's switch condition, "if it doesn't look good during the process", is made concrete as review points. At each checkpoint, record the result in `plan/` and decide **continue A** or **switch to C**. The time budgets are suggestions for the user to confirm or change.

| # | Checkpoint | Pass criterion | Suggested budget | Switch signal |
|---|---|---|---|---|
| CP1 | **Data understood** | Tools list and extract all `.pac` (`ARC`/`cmp`), decode HCA from `.awb`, read ACB cues, read note charts (`score.pac`), models and textures | 2-3 months | A core format stays unreadable (for example encrypted, or charts undecodable) |
| CP2 | **Vertical slice** | One song plays natively: chart + music + judgement + simple 3D/2D view; timing within ±1 frame of the console (compare against the user's PS4 or shadPS4) | +4-6 months after CP1 | Scoring/judgement rules cannot be recovered from the eboot with reasonable effort; or shader/render needs dwarf the budget |
| CP3 | **Breadth estimate** | Inventory of all screens and systems (menus, story/talk, costumes, items, missions, profile cards, DLC, saves), with recovered-logic estimates | at CP2 | Estimated remaining work is several times the time spent so far |
| CP4 | **Feature-complete path** | Menus and main loop playable | per CP3 estimate | Repeated slips beyond the CP3 estimate |

Independent of A's progress, a **cheap probe of C** is advised early: build shadPS4 in `work/` (needs the Vulkan SDK and a toolchain; ask the user first) and record how far SIF boots. The result informs every checkpoint above.

## 5. Switch rules

- Switching from A to C is the user's decision at a checkpoint, recorded in a new `<timestamp>-plan.md` in this folder.
- On a switch:
  - the port becomes GPL-2.0;
  - the A work carried over is: data tools, timing/input/settings/installer layers, test runner;
  - a new plan revision replaces Parts 9-10 scope with the C items in section 6.
- Revisit A as primary if: CP1 shows a blocking format; the C probe boots SIF to menus with little effort; or the user's priorities change (for example, a working game soon over license independence).
